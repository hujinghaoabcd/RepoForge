# RepoForge Init

`repoforge init` creates one combined `repoforge.yml` for an existing repository.

It does **not** inspect the repository and guess a project type. You explicitly choose the project family and README profile:

```bash
repoforge init . \
  --type scientific-python \
  --profile standard
```

The generated file records that selection:

```yaml
repoforge:
  config_version: 1
  project_type: scientific-python
  profile: standard
```

After that, `apply` can read the type/profile from the config:

```bash
repoforge apply . --config repoforge.yml --dry-run
repoforge apply . --config repoforge.yml
```

## What init combines

RepoForge starts from the selected README profile's `config.example.yml`, then adds the reusable repository-standard configuration sections:

```text
README profile config
        +
community standards config
        +
GitHub Issue / PR config
        +
citation / changelog config
        ↓
repoforge.yml
```

The result contains the configuration needed by both the README renderer and the repository standards renderer.

## Recommended first command

For a real repository, provide the project name and repository URL at initialization time:

```bash
repoforge init /path/to/project \
  --type research-algorithm \
  --profile full \
  --name MyMethod \
  --repository-url https://github.com/example/my-method
```

If `--name` is omitted, RepoForge uses the target directory name. If `--repository-url` is omitted, the generated starter config uses the visible placeholder:

```text
https://github.com/OWNER/REPOSITORY
```

Replace that placeholder before applying repository standards.

## Init is a starter, not content inference

The selected README configuration is based on that profile's maintained example configuration. RepoForge replaces the example project identity where it can do so safely, but it does not claim to understand your scientific method, deployment topology, API, package imports, benchmark protocol, or product behavior.

Before applying, review at least:

- project name, tagline, and positioning;
- logo and badges;
- installation and verification commands;
- runnable examples;
- documentation/navigation links;
- project-specific limitations and compatibility statements;
- contribution commands;
- Code of Conduct reporting contact;
- security reporting instructions;
- support channels;
- Citation authors, version, license, DOI, URL, and keywords;
- changelog policy and initial entries.

The generated file begins with a reminder to review these values.

## Overwrite safety

RepoForge refuses to replace an existing config by default:

```bash
repoforge init . --type web-application --profile standard
```

If `repoforge.yml` already exists, the command fails. To intentionally regenerate it:

```bash
repoforge init . \
  --type web-application \
  --profile standard \
  --force
```

`--force` applies only to the config file generated by `init`. It does not imply `repoforge apply --force`.

## Custom output path

The default output is:

```text
<target>/repoforge.yml
```

Use another path when needed:

```bash
repoforge init . \
  --type desktop-application \
  --profile full \
  --output config/repoforge.yml
```

## Explicit CLI overrides

A config created by `init` stores project type and profile, so the normal apply command is short:

```bash
repoforge apply . --config repoforge.yml
```

You can still explicitly override the stored selection for a one-off run:

```bash
repoforge apply . \
  --config repoforge.yml \
  --type scientific-python \
  --profile minimal \
  --dry-run
```

This is an explicit override, not project detection.

## Suggested workflow

```text
repoforge init . --type ... --profile ...
        ↓
edit repoforge.yml
        ↓
repoforge apply . --config repoforge.yml --dry-run
        ↓
review create / unchanged / overwrite actions
        ↓
repoforge apply . --config repoforge.yml
```

The next repository workflow layer can build on the same config for `diff` and `check` without adding automatic project-type inference.
